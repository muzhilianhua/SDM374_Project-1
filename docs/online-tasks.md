## 全局目标与主线

在线阶段的成绩：超过我们离线结果（离线最好 R = 115.68，提交 2，见 decisions.md Findings）得 8%，组间排名得 5%（取最好的一次调用）；另有代码、创新点和报告分。
规则：提交一份冻结、可复现的脚本，在课程电脑上**最多顺序调用评估器 20 次，每次最多 50 组权重**；
第 1 次调用前只能使用 2048 条训练数据；每次调用取批内最低 R，成绩取所有调用中的最低值；
同一点不得重复评估（决策 19、20、22）。
正式运行交的是独立的 `submission/` 目录（决策 31，依据助教 11-12 课上的要求）：基于课程 `run.py`，只含 2048 条训练数据，模型每次调用从数据重新拟合（超参数是常数），每次调用写一个可追溯的 checkpoint。`sdm` 继续用于开发、回放和报告。

## 3.2 在线运行框架

### T06 评估器接口
- **原因**：同一个在线主循环要对接三种"评估器"：正式运行用真实 `solver.exe`，回放用表格查值或半合成真值，测试用快速替身。如果每处都各写一遍调用代码，正式运行和回放就无法保证跑的是同一套逻辑。
- **内容**：定义一个评估器接口（输入最多 50 组权重，返回 R 列表），实现以下几个版本：
  - 真实 solver：stdin JSON、解析 `{"R": [...]}`、退出码 2 时报错并保留 stderr、超时按 50 组约 5 分钟设置、正式模式下绝不删除 `usage.count`。
  - 表格查值版。
  - 半合成真值版。
- **作用**：T08、T17、T19 和测试共用一个入口，保证回放结论能迁移到正式运行。
- **产出物**：`src/sdm/` 中的评估器模块和单元测试；`docs/interfaces.md` 中新增的接口说明。

### T07 调用日志
- **原因**：20 次调用是唯一能计分的数据，必须完整、不可篡改地记录下来。续跑（T08）、并入训练数据（T08、T13）、画曲线（T26）都要读这份日志。
- **内容**：定义 `online_log.csv` 的字段（调用号、批内序号、21 个权重、R、来源策略或分组、run id、时间），实现只追加写入；读取时校验字段和调用号连续。
- **作用**：作为在线阶段唯一的事实来源，保证结果可追溯，失败后可以恢复。
- **产出物**：日志格式说明（写入 `docs/interfaces.md`），读写函数及测试。

### T08 在线主程序
- **原因**：比赛交付的就是这个程序。它要把"提议 → 检查 → 调用 → 记录 → 重训"自动串起来，任何一步出错都可能浪费额度或违规。
- **内容**：实现 `sdm online -c <配置>`（名称可定），每次调用依次：
  1. 用 2048 行 + 已有日志重建 `X, y`，训练代理模型。
  2. 由策略提出最多 50 个点。
  3. 提交前检查：单纯形约束、与训练行和已发送点去重、批大小、剩余额度。
  4. 调用评估器，写日志。
  5. 进入下一次调用。

  程序中断后从日志续跑，已发送的批不再重发。
- **作用**：把模型和策略组装成可交付的脚本；回放器（T17）也复用这个循环。
- **产出物**：CLI 命令、在线配置模板 `experiments/online-*.toml`、端到端测试（使用 T06 的替身评估器）。

### T09 跨机器确定性
- **原因**：决策 22 要求在课程电脑上重跑时发出完全相同的批次。11-12 在课程电脑上实测：`histgb` 和 `extratrees` 的预测与本机逐位一致，`local-gp` 差约 1e-6，`xgboost` 明显不同。一个点的差别就会让后续所有批次都不同。决策 31 把超参数固定为常数，去掉了一个已知的差异来源；但 BLAS 内核、线程数和归约顺序同样会造成差异，所以"跨机器一致"是要验证的目标，不是设计本身的保证。
- **内容**：用 `submission/` 的 `--evaluator synthetic` 在本机和课程电脑上各跑满 20 次调用，比较每次调用的规范记录（决策 31：权重、R、策略与 RNG 状态，JSON 键排序、浮点用 `float.hex` 精确写出，不含时间戳、路径、主机名、耗时和 solver 原始输出），要求逐位相同；不一致时报出第一个不同的调用号和字段。checkpoint 的 manifest 哈希链只检查目录有没有被改过，不用于跨机器比较。若有差异，按决策 31 的顺序降级：先固定 OpenBLAS 内核（`OPENBLAS_CORETYPE=Prescott`）并把 `OMP_NUM_THREADS`、`MKL_NUM_THREADS`、`OPENBLAS_NUM_THREADS` 设为 1，再不行就在排序候选前把预测值量化到固定网格（如 1e-4），平分时按权重的字典序决定。PR #25 已测到（超参数运行时优化、内核已固定）：强制改成 8 或 1 线程会让个别批次不同，但 12 核电脑用默认线程数与 20 核的参考运行 20 批全部一致。所以线程数可能影响结果，但影响不是单调的，不要求各台机器线程数相同，以每台机器上的实际比较为准。
- **作用**：作为提交包的验收测试，保证本地演练的结果就是正式运行的结果。
- **产出物**：比较脚本与结果记录（两台机器的环境信息、每次调用的比较结果、采用了哪一级降级），必要的配置或代码修改。

### T10 课程电脑运行包
- **原因**：助教在 11-12 课上要求最终提交尽量精简、基于已有的 `run.py`、只含 2048 条训练数据、模型从零训练、有可追溯的 checkpoint。临时运行包（`feat/course-pc-kit`）打包了整个仓库、Python 和全部依赖，不符合"精简"，也带上了 `analysis/` 下的本地实测日志。课程电脑的环境已经查清：Win10、Python 3.14、装有 uv、能连 PyPI 和 GitHub（11-12 实测，记录在 PR #20 的 decisions.md Resolved）。PR #25 的验证包 `analysis/online_rehearsal/package_v4s7/` 已经有 `check` / `verify` / `run`、固定依赖和文件校验，`submission/` 从它改起。另外 #28：一台 Windows 11 24H2 电脑上外层 `solver.exe` 收到的 stdin 是空的（退出码 2，`Expecting value`），正式运行依赖的正是这条通道。
- **内容**：按决策 31 建立 `submission/`：
  1. `run.py` 沿用课程 `run.py` 的结构（20 次循环，PowerShell 把 `weight.json` 管道给 `solver.exe`），把两处 todo 填成"读 R → 重训 → 写下一批 `weight.json`"；删掉课程 `run.py` 第 43 行"可以删掉 usage.count 文件重置计数"的注释，程序本身从不碰 `usage.count`；README 区分两份 exe：正式运行那份不能删 `usage.count`，开发副本可以在两次演练之间删掉它重置额度（T19 跑多个种子需要）；
  2. `solver.exe` 不放进包里：用 `--solver <路径>` 指定，默认是 `run.py` 同目录下的 `solver.exe`；启动时计算它的 sha256，与 README 中记下的值（来自 `solver/CHECKSUMS.sha256`）比较，不一致时打印警告并写进每个 checkpoint，但不中止运行（以课程电脑上的 exe 为准）；
  3. 第 1 次调用之前：先写入并 fsync `checkpoints/run.json`（`config.json`、`train.csv`、`run.py`、`policy.py`、`surrogate.py`、`solver.exe` 的 sha256）；再发一组故意不合法的权重（含负数，被拒的输入不扣次数，决策 28），stderr 必须是 solver 自己的权重检查信息，否则说明 stdin 没有送到（#28），直接停止；
  4. 调用 solver **之前**先写入并 fsync `checkpoints/call_<kk>.sent.json`（这批的权重），从这一刻起这批算已发送，调用完成后也保留；调用之后写 `checkpoints/call_<kk>.tmp/`（发出的 `weight.json`、solver 原始输出、R、策略与 RNG 状态、超参数、`train.csv` 的哈希与行数、`solver.exe` 的哈希、`manifest.json` 哈希链，第一环是 `run.json`），全部文件 fsync 后整体改名为 `call_<kk>/`；只用 JSON / `.npz`；
  5. 退出码：0 且能解析出 R 才算完成；2 表示 solver 在评估前就拒绝了（输入不合法、stdin 为空或 `Usage limit reached`），把 `.sent.json` 改名为 `call_<kk>.rejected.json` 并写入 stderr，这次不计数，打印原因后停止，不自动重发，由人决定能否修正后再发（决策 28）；solver 启动后的其他失败（其他退出码、超时、崩溃、输出里没有 R）都按"已发送、无 R"处理；
  6. 续跑规则：`call_<kk>/` 存在、每个文件都与 manifest 一致、与上一次 manifest 的链接也对得上，才算完整。只自动处理最后一次调用：有 `.sent.json` 却只有 `.tmp` 或没有 `call_<kk>/` 的，这批按决策 28 记为"已发送、无 R"，这次调用算已用，永不重发；更早的某个 `call_<kk>/` 校验不符或链接断开时，停止并报出是哪个目录，不自动猜测。`config.json`、`train.csv`、`run.py`、`policy.py`、`surrogate.py` 任一哈希与 `run.json` 不同，就拒绝续跑；
  7. 评估器：默认 `--evaluator solver`，正式运行只用它；`--evaluator synthetic` 供测试和 T09 使用；`--evaluator <模块>:<类>` 只在开发时用，从包外加载评估器，T17 / T18 的回放真值通过它驱动冻结策略；
  8. `pyproject.toml` + `uv.lock`（Python 3.11、numpy 1.24.4、scipy 1.10.1、scikit-learn 1.2.2）和 README，启动命令只有 `uv run run.py`。

  策略本身由 T15 写入 `policy.py` / `surrogate.py`。
- **作用**：这就是正式运行要交的东西；T09、T19、T21 都在它上面做。
- **产出物**：`submission/` 目录；checkpoint 与续跑的测试（至少覆盖：solver 运行中崩溃后不重发、`.tmp` 目录被忽略、更早的 checkpoint 损坏时停止、第 1 次调用中崩溃后改动代码会被拒绝续跑、退出码 2 不计数且停止、stdin 检查失败时停止）；在干净 Windows 机器上验证通过的记录。

## 3.3 代理模型

### T12 在线代理模型选择
- **原因**：离线阶段按 v3.2 分数排出的模型，不一定最适合在线循环。在线时数据逐批增加，需要每次快速重训，并且要在搜索区域内预测准确。离线结果表明，boosted trees 在被搜索的区域过于乐观（提交 1 预测 107–111，实测 119.7）。
- **内容**：在回放器上比较 GP、local-gp、boosted trees、stack 等候选模型，看逐次最优值、预测与实测误差和重训耗时，选定策略使用的模型及其参数。
- **作用**：决定在线策略的"眼睛"，直接影响成绩。
- **产出物**：比较结果（带 run id），推荐的模型配置，记入 decisions.md。

### T13 在线重训与误差报告
- **原因**：每次调用后都有 50 个新的真实点，这是检验和修正模型的最好机会；同时需要量化模型在新区域预测得准不准。
- **内容**：主程序每次重训时，记录上一批的预测与实测误差（平均误差、最低点误差、std 覆盖率），写入运行记录或日志。
- **作用**：发现模型系统性乐观或悲观时可以修正；也为报告提供"预测与实测"的证据。
- **产出物**：重训与误差记录的代码和测试，演练中每次调用的误差表。

### T14 不确定度校准
- **原因**：策略的探索部分依赖 `std` 判断哪里值得去试。如果 `std` 太窄，就只会围着已知点打转；太宽，则会浪费点数。
- **内容**：让所选模型的 `std_coverage` 落在 0.55–0.80 之间；可选对信赖域附近的样本加权，提高局部精度。
- **作用**：让探索和利用的分配有依据。

### T35 GP-ARD 假设检验
- **原因**：团队的 GP-ARD（`bayes-search`、`additive-ard`）是离线阶段排名最高的平滑模型，也是在线策略的候选"眼睛"。它的结论依赖一组假设：函数确定、可按楼宇相加、平稳、先验均值为常数、残差近似高斯、不确定度校准。这些假设是否成立，此前没有用训练表之外的真实数据检验过。
- **内容**：用训练表的随机留出和本地 solver 日志（`analysis/replay/evidence/`，决策 27 允许用于选择模型，但不写进提交代码）逐项检验上述假设；比较通用 ARD 核族；在三个区域分别重拟合检验平稳性；测试趋势项、log 目标、每栋楼各自长度尺度三种改进。
- **作用**：告诉 T12 选模型时该看什么、T14 校准时该放大多少 `std`，也说明代理模型为什么找不到远离训练数据的低值区。
- **产出物**：`analysis/gp_assumptions/`（`study.py`、README、带 provenance 的结果副本）。
- **产出物**：校准后的模型或参数，`sdm evaluate` 的 run id 与覆盖率指标。

### T36 评估器低值点研究（仅研究）
- **原因**：代理模型在远离训练数据的低值区预测不准（T35）。要知道评估器里到底能低到多少、低值点长什么样，只能直接查询评估器。
- **内容**：用本地 `solver.exe` 副本不限次数地做黑盒搜索（按楼分解的多尺度搜索 FMS），再做机理探针：单目标基线与敲除、楼间分工析因、r 的细扫、次要权重的剂量曲线、极小权重与 0 的比较、逐坐标扫描。只在研究目录自己的 `workers/` 里重置 `usage.count`。
- **作用**：给 T15、T18 的策略设计提供认识（例如逐坐标扫描小权重是随机扰动会漏掉的移动方式），给报告提供"评估器地形"一节的材料。按决策 19、27、29，这里的点、R 值和权重都不得写进在线代码、配置、热启动或排除表。
- **产出物**：`analysis/lowr_search/`（脚本、`eval_log.jsonl`、各实验结果、图、`provenance.json`、README）；给 T08、T12–T16、T18、T19 的指导意见在 `analysis/lowr_search/GUIDANCE.md`，其中引用的先验只用训练表推出（`train_priors.py`）。

## 3.4 提议策略

### T15 批量提议策略
- **原因**：成绩只看批内最低值，所以每批 50 个点的目标是"让其中一个点尽可能低"，而不是平均值低。T37（PR #25）在本地真实 solver 上验证了一个合规的分块下降策略（每个候选只改一栋楼，下一次调用组合各楼的最优改动），推荐版本 v4 在 3 个种子上为 108.05 / 103.275 / 105.44，平均 105.59（v2 平均 106.52）。但它是 `analysis/` 下的原型：局部 GP 每次调用都优化超参数，会破坏跨机器一致性（PR #25 的验证包已测到强制改变线程数时个别批次不同）。
- **内容**：按决策 31 把 T37 的推荐版本（目前是 v4，`policy_v4.py`）写成 `submission/policy.py` 和 `surrogate.py`：超参数改为 `config.json` 中的常数，每次调用只重新拟合；多排一些候选，补足被去重丢掉的点，保证每批 50 个互不重复的新点（不与训练行或已发送点重复）；只用训练行推出的先验（决策 27）。`submission/` 是冻结策略的唯一实现（决策 31），不再和 `sdm` 做逐批对照；测试直接针对 `submission/`：同一机器上重跑两次批次完全相同，每批 50 个点都通过单纯形约束且互不重复，被去重丢掉的点能补足。
- **作用**：这是决定成绩的核心算法。
- **产出物**：`submission/policy.py`、`submission/surrogate.py`、`config.json` 中的策略参数和测试。

### T16 信赖域半径自适应
- **原因**：固定的搜索半径要么太保守，要么容易外推。离线结果显示，离数据太远的点实测会明显变差（baseline W\*、提交 1）。
- **内容**：仿照 TuRBO，当前批若刷新最优值就扩大半径，若没有就缩小，并设定上下限。
- **作用**：在 20 次调用内自动平衡大胆与稳妥。
- **产出物**：策略中的半径更新逻辑、参数和测试；在回放中与固定半径的对比。

## 3.5 回放与分析

### T17 离线回放器
- **原因**：正式运行只有一次，而本地用真实 solver 完整跑一遍要 2–4 小时（PR #25 实测每次 50 组的调用 5–11 分钟），并且用它调参还可能不被允许（T03）。所以需要一个又快又合规的环境，来比较不同模型和策略。
- **内容**：复用 T08 的主循环，把评估器换成以下两种之一：
  - 表格留出池：从 2048 行中留出一部分当"未知"，策略只能从池中选点。
  - 半合成真值：用拟合的模型当真实函数，沿用 `analysis/coupling/` 的方法。

  输出每次调用的最优值曲线，固定种子可复现。
- **作用**：作为 T12、T18 的实验平台，也为报告提供策略对比的主要证据。
- **产出物**：`src/sdm/replay.py`、回放配置、测试，以及曲线和结果文件（带 provenance）。

### T18 策略参数比较与推荐
- **原因**：T15 和 T16 留下的参数（利用 / 探索比例、半径、模型选择）需要用证据来定，而不是凭感觉。
- **内容**：在回放器上做有限规模的参数比较（多个种子、两类真值），报告逐次最优值曲线和最终最低值的分布，给出候选配置及其理由。比较冻结策略本身时直接运行 `submission/`，回放真值通过 `--evaluator <模块>:<类>` 接入（决策 31）。T18 只给候选；`config.json` 里冻结的超参数常数由 T19 确定，常数来源只引 T19，避免同一个常数有两个出处。
- **作用**：缩小 T19 要在真实 solver 上验证的范围。
- **产出物**：比较结果与推荐配置 `experiments/online-*.toml`，记入 decisions.md。

### T19 真实评估器完整演练
- **原因**：回放用的是替身，只有真实 solver 能检验整条链路：耗时、输出格式、额度计数、模型在新区域的真实误差。决策 31 把 GP 超参数改成常数后，T37 的结果（v4 平均 105.59，最好 103.275）不能直接沿用，需要重新测。
- **内容**：用 `submission/` 在本地真实 `solver.exe` 上完整跑 20 × 50（多个种子，每次 2–4 小时：PR #25 实测每次 50 组的调用 5–11 分钟；用开发副本，每次演练前删掉 `usage.count` 重置额度，决策 31），从 T18 的候选中确定 `config.json` 中的超参数常数并写明来源（`config.json` 只引 T19），对比固定超参数与 T37 原型的结果和预测误差。PR #27 的那次 20 × 50 演练（R = 105.9905）用的是旧口径，不是 `submission/` 的运行，而且调用的是从 `solver.exe` 里拆出的内层程序（助教 11-16 答复：只能用于内部探索，见 #28），只作参考。据此调参的前提是决策 27（助教尚未确认）；选种子属于 decisions.md 中关于调参的待决问题，不在本任务中决定。
- **作用**：在冻结前发现运行层面的问题，确定超参数常数，并预估正式成绩。
- **产出物**：演练日志（含 checkpoint）、误差与耗时报告、超参数常数及其来源、发现的问题清单。

### T20 机理笔记（P2）
- **原因**：理解权重如何影响 R（楼内比例、楼间可加性、2 号楼低敏感度），可以给模型提供先验，也能丰富报告的分析部分。
- **内容**：基于训练数据和已有的真实点做分析，整理成可以落实到模型或策略的先验。
- **作用**：可能提高模型精度；为报告提供讨论素材。
- **产出物**：`analysis/mechanism/README.md` 及其分析脚本。
